# Integrations and infrastructure

## Phase 5 Windows helper (checked 2026-10-23)

Project-local Python 3.10.11 venv pins `pywinauto==0.6.9`, `psutil==7.1.3`, `Pillow==12.3.0`, `comtypes==1.4.17`, `pywin32==312`, and `six==1.17.0` in `packages/desktop-adapters/windows/requirements.txt`. pywinauto 0.6.9 was the current stable PyPI release checked on this date; 1.0.0b1 is a prerelease. The helper uses documented UIA `Desktop.windows`, wrappers, focus, edit text, and window capture. It runs locally through bounded JSON-lines stdio, not a network port. UIA and foreground operations require an unlocked interactive desktop; Windows can deny `SetForegroundWindow`. The target run used Windows 10.0 build 26300, DPI 120, one monitor. VS Code 1.140.0 was observed; Notepad packaged app 11.2607.14.0 did not match the System32 launcher identity.

## Phase 3 desktop (implementation in progress)

Electron stable `45.0.0` and `ws` `8.22.0` are pinned in `apps/desktop/package.json`; the API uses `ws` for its worker WebSocket endpoint. Electron release/security/safeStorage/dialog documentation and the `ws` package/release pages were checked on 2026-10-22. Electron's asynchronous OS-backed safeStorage API is used; secure-storage unavailability is fail-closed. The worker initiates an outbound WebSocket, mapping HTTPS to WSS, permitting WS only for loopback HTTP, and uses Ed25519 challenge-response. There is no certificate-verification bypass. Protocol v1 messages are validated and capped at 256 KiB. No live Electron/WebSocket/device demonstration was possible in this environment.

References checked 2026-10-22: [Electron releases](https://releases.electronjs.org/?channel=stable), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security/), [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage/), [Electron directory dialog](https://www.electronjs.org/docs/latest/api/dialog), [`ws` package](https://www.npmjs.com/package/ws), [`ws` releases](https://github.com/websockets/ws/releases). Windows remains the provisional target; no OS runtime behavior is verified. Device protocol transport is currently hosted in the API process, while Phase 1 queue workers are separate processes; Phase 2 does not yet dispatch filesystem tools to this gateway.

## Phase 4 browser automation (implemented source; partial fixture verification)

The desktop package pins official Playwright `1.64.1` (npm `latest` stable checked 2026-10-22); the package page lists bundled Chromium revision `156.0.8078.4`. Official installation guidance lists Node.js 22.x as supported; this workspace uses Node `22.18.0`. Browser automation source runs on the paired desktop, not the API host. It launches a visible Chromium persistent context under Electron app user data, never attaches to the owner's normal browser profile, enables Chromium sandboxing, and blocks service worker registration for request-policy visibility. No custom browser security-disabling flags are used.

Current source includes bounded structured inspection/read, page IDs, snapshot-scoped opaque element references, verified fill/check/select, conservative click refusal for submit-like and unknown consequential actions, root-authorized upload/download, and popup/tab handling. URL checks allow credential-free HTTP(S), reject local/private destinations and resolve/check DNS addresses; routed requests repeat checks. This is defense-in-depth, not an OS network sandbox or guarantee against DNS rebinding. Fixture localhost allowance is explicit and is not enabled by production initialization. The controlled browser fixture has run successfully for the tested paths; agent-to-worker/API end-to-end and real-site acceptance remain unverified.

Official references checked 2026-10-22: [Playwright installation and system requirements](https://playwright.dev/docs/intro), [persistent context API](https://playwright.dev/docs/api/class-browsertype), [service workers](https://playwright.dev/docs/service-workers), [downloads](https://playwright.dev/docs/downloads), [Playwright release notes](https://playwright.dev/docs/release-notes), [Playwright npm release](https://www.npmjs.com/package/playwright). Runtime verification covered the controlled fixture only. Exact submission approval is not integrated; consequential clicks fail closed. The API dispatch source path is not runtime-tested and the Phase 3 API-hosted gateway/queue-worker process boundary remains an integration limitation.
